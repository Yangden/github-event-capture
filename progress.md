### CRITICAL infra finding — test was hitting REAL AWS SQS (now fixed test-side)

The prior `LocalStackSqsTestConfig` override of the `sqsAsyncClientCloud` bean was **not taking
effect**. With the plain `@Bean` + `allow-bean-definition-overriding=true`, the client injected
into `AsyncQueueserviceImpl` was actually the *production* bean (`endpointOverride=empty`) — the
test's `@Import` and the app's component-scanned `SqsConfiguration` registered
non-deterministically and production won. Because this machine has ambient AWS credentials
(`AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` set; `aws sts get-caller-identity` → account
`038462794128`), the production bean's STS AssumeRole succeeded and alert messages went to the
**real** `EventNotificationsQueue`. Any run where the alert path executed against the
mis-injected client (i.e. after the `@Disabled` tests were re-enabled but before this fix) sent
real messages to production SQS.

**Owner decision (2026-07-25): stage is local-only, cloud/prod SQS is out of scope** — the
prod-queue check/purge is NOT an action item. The test is now correctly pinned to LocalStack
(verified `endpointOverride=localhost:4566`), so future runs stay local. The subagent could not
verify prod queue depth anyway (IAM user lacks `sqs:GetQueueAttributes`; assuming the app role was
correctly blocked as out-of-scope).

Fix (test-only, in `LocalStackSqsTestConfig.java`): replaced the plain `@Bean` with a
`BeanDefinitionRegistryPostProcessor` that unconditionally removes and replaces the
`sqsAsyncClientCloud` definition after all config classes register theirs — order-independent.
Verified via a temporary diagnostic that the injected client resolves to
`endpointOverride=Optional[http://localhost:4566]` before any message-sending scenario ran.
No assertions were weakened; scenarios 1/4/5 pass because messages now actually reach the
LocalStack queue the test polls.

### CRITICAL bug found (production-breaking, src/main not modified)

`IssueAlertServiceImpl.queryOpenIssues()` groups on `issueInfo.id`, but Spring Data MongoDB
silently remaps any property named `id` — including on the nested `IssueInfo` object — to
`_id`. The persisted field path is actually `issueInfo._id`, so the group key evaluates to
`null` for every document, all issues collapse into one pseudo-group, and mapping `null`
into `OpenIssueResult`'s primitive `long issueId` throws `MappingInstantiationException`.

**Net effect: `scanAndAlert()` crashes whenever at least one issue is genuinely past its TTL
— the exact case the feature exists for.** The unit tests could not catch this because they
mock `mongoTemplate.aggregate`. Verified by isolated probes: grouping on `issueInfo._id`
maps correctly against the same persisted documents.

**Fix (pending):** change the group path to `issueInfo._id`, then re-enable the three
`@Disabled` tests (they are the regression proof for the fix).

### Secondary bug found (documented, not fixed)

`KafkaDatabaseConsumer` uses a bare `new ObjectMapper()` with no `JavaTimeModule`, so it
cannot deserialize `Instant` fields. Any real GitHub issue webhook carrying `created_at`
would fail to persist. The test's own seeding ObjectMapper registers `JavaTimeModule` to
work around this.

### Environment findings (test-side workarounds, worth knowing)

1. **Every `@SpringBootTest` in this repo fails to start** out of the box:
   `MonitorServiceImpl` requires a `PrometheusMeterRegistry`, but Spring Boot Test disables
   metrics export by default. Pre-existing issue (reproduced on the unmodified
   `GithubEventCaptureApplicationTests`). Workaround: `@AutoConfigureObservability`.
2. `EventNotificationImplConcurrency`'s `@PostConstruct` background poller shares the same
   queue as the code under test and races to drain messages before assertions run.
   Neutralized with `@MockBean`.
